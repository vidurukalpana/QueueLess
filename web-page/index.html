Less waiting, more customers.

QueueLess is a virtual queue web app for small shops. Customers join from their phone, then wait anywhere instead of sitting in the shop.

The Problem

Waiting in line wastes everyone's time

Customers at small shops often wait 30–90 minutes without knowing their position. Many walk away when they see a crowd, so shops lose business.

The Solution

One queue, two simple views

QueueLess moves the queue to the customer's phone. Customers join by QR code, wait anywhere, then return when their turn is near. The owner runs everything from one simple dashboard.

📱

Customer view (no login)

  • Scan a QR code, or open a share link
  • Enter a name, get a ticket number
  • See live position with estimated wait
  • Get alerted when your turn is near
💈

Owner dashboard (login)

  • Create queues with a QR code
  • Call next, skip or mark done
  • See who has arrived
  • Check daily stats

Features

What the system does

QR code with share link

Join at the shop by QR, or from home by link.

Live position

Position with estimated wait, updated instantly.

Smart wait estimate

Uses today's real service time, else the queue default.

Owner controls

Call next, skip, done, pause, close.

Queue settings

Block remote joins, or set a maximum queue size.

Arrival check-in

I'm here marks a customer as present. QR joins check in automatically.

Turn alerts

Sent once when two people are ahead, again on your turn.

Daily ticket numbers

Numbers restart at 1 each day. Old tickets clear themselves.

Automatic reconnect

If the network drops, the page reconnects by itself.

Ticket life cycle

waiting → called → done

A ticket can also leave the queue as skipped (by the owner) or cancelled (by the customer, or automatically the next day).

Architecture

Three simple parts

CI/CD: GitHub → GitHub Actions (Lint, Test, Build) → Auto-deploy from main

Frontend = the shop window

Shows screens in the browser. It makes no decisions by itself.

Backend = the manager

Checks every request, applies the rules, then tells all screens.

Database = the record book

Keeps every owner, queue and ticket safely.

Data Flow

How one action reaches every screen

A. Customer joins

  1. Customer scans the QR code
  2. React sends the name to the REST API
  3. Go locks the queue, checks the rules, then saves a ticket
  4. The phone stores a secret ticket token
  5. The WebSocket hub broadcasts queue_updated

B. Owner calls next

  1. Owner clicks Call next, sending the JWT
  2. Middleware checks the token, then ownership
  3. A database transaction marks the ticket called
  4. The hub broadcasts the change
  5. The customer sees Your turn!, others move up

C. Customer arrives

  1. Remote customer reaches the shop
  2. Taps I'm here, sending the ticket token
  3. Go saves the check-in time once
  4. The hub broadcasts the change
  5. The owner sees a Here badge

Security

How the system stays safe

RiskProtection
Stolen passwordsHashed with bcrypt, never stored as plain text
Owners touching other queuesJWT check, then ownership check on every request
Faking another ticketEach ticket has a secret token only its holder knows
Password guessing, spam joinsRate limiting per IP
Two customers, one numberDatabase row locks in a transaction
SQL injectionParameterized queries through sqlc
Requests from other websitesCORS, WebSocket origin checks
Remote no-showsShop-only mode, maximum queue size, arrival check-in
